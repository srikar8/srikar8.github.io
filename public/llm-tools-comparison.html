LLM architecture

Route. Observe. Test.
One stack, three distinct jobs.

LiteLLM handles model access. Langfuse explains what happened. Promptfoo checks whether the system behaves as expected. OpenTelemetry and OTLP connect their telemetry.

01 / Model gateway & SDK

LiteLLM

“How do we call and control our models?”

Primary jobProvide a common model API and route requests across providers.
Key functionality
  • Unified provider interface
  • Routing, retries and fallbacks
  • Gateway keys and access controls
  • Budgets, rate limits and spend tracking
Where it runsIn application code as an SDK, or between your app and providers as a proxy.
Main outputModel responses, usage information and request telemetry.
OTel / OTLP roleTrace producer. Its OpenTelemetry integration exports model-call spans to a backend such as Langfuse.
Choose it whenYou need shared model access, routing and operational controls.
02 / LLM observability

Langfuse

“What happened, and why?”

Primary jobRecord and inspect application traces, usage, cost and quality.
Key functionality
  • Nested traces and debugging
  • Latency, token and cost analysis
  • Prompt management and versioning
  • Datasets, experiments and evaluation scores
Where it runsA cloud or self-hosted backend; SDKs and instrumentation run inside your app.
Main outputTrace timelines, dashboards, prompts and evaluation records.
OTel / OTLP roleTrace receiver. Accepts OTLP over HTTP directly. Its SDKs create and export application spans.
Choose it whenYou need to understand real requests and monitor quality over time.
03 / Evaluation & red teaming

Promptfoo

“Does this pass our tests?”

Primary jobRun repeatable quality and security tests against prompts, models or apps.
Key functionality
  • Prompt and model comparisons
  • Assertions and grading
  • Regression tests in CI
  • Red-team attack scenarios
Where it runsA local or CI test runner, with a UI to inspect evaluation results.
Main outputPass/fail results, scores, comparisons and security findings.
OTel / OTLP roleTest-time trace receiver. Its built-in OTLP receiver links app traces to evaluations; trace-aware checks can inspect execution.
Choose it whenYou need measurable checks before shipping or after a change.

Shared telemetry foundation

OpenTelemetry + OTLP Supporting all three, with different roles

OpenTelemetry (OTel) provides APIs, SDKs and instrumentation to create spans and export telemetry.

OTLP is the protocol that transports that telemetry to a compatible receiver. Here, the diagrams focus on traces over HTTP.

Keep the connections separate: model requests use model or application APIs; traces use OTLP. W3C traceparent propagates trace identity between services. OTLP itself does not route model calls, execute tests or manage prompts.

Where functionality overlaps

Several features appear in more than one tool. Choose by the job you need to complete: serving model traffic, understanding production behavior, or testing a change. These are practical recommendations based on each tool's main workflow.

Start with LiteLLM

“We need reliable model access.”

Good when several applications or teams need common provider access, routing, budgets and controls.

Start with Langfuse

“We need to understand our app.”

Good when you need production traces, prompt versioning and quality analysis tied to real behavior.

Start with Promptfoo

“We need confidence in a change.”

Good when you need model comparisons, regression tests or repeatable security testing.

Use all three when you need the full loop: LiteLLM serves model traffic, Langfuse reveals production behavior, and Promptfoo tests improvements before release. A production failure can become a regression test; its trace helps explain why it failed.
